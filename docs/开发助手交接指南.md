# 银行 Agent 开发助手交接指南

这份交接说明供 GLM-5.3-Flash、Qwen3.8-Max、Gemini 3.8 Flash（`gemini-3.8-flash`）或其他开发助手接手安言仓库，继续修复银行对话链路并完成稳定验收。开发模型需要运行在能够读取仓库、修改文件、执行命令和查看测试结果的开发工具中；只有聊天或模型 API 接口，不能自行完成服务器和设备验收。

**开发助手换模型，不代表银行运行模型换模型。** 当前银行 Agent、回答核验、模拟用户和评分器仍使用 `deepseek-flash`。除非用户另行明确要求，不修改运行模型、思考模式或验收标准。更强的开发模型可以帮助定位和审查修改，但任务通过与否以运行证据为准。

## 最终交付目标

交付一个在已登记银行能力范围内能理解自然表达、承接多轮追问并稳定办理的 Agent：查询直接回答当前对象和字段，解释与可行性咨询不触发办理，明确办理后才生成提案，确认和强验证通过且 Core 持久提交成功后才能报告成功。暂停、恢复、纠正与取消需作用于正确任务；不支持或证据不足时准确说明边界，推荐问题只引导已可回答的能力。

这些行为要覆盖跨场景、不同说法和话题切换，不能只修一个测试句。完成标准为本文“完整验收门槛”全部满足，并交付同候选报告、故障与设备证据、真实观察和独立人工复核、发布检查及稳定候选包。Git push、局部通过或生成复核包都不是终点；部署与线上验收需按用户届时的明确安排执行。

**当前执行范围：业务开发与评测已按用户明确指令“继续开发与验收”恢复。** 已落地开发提速设施（受控并发评测、账本在途限流、判官额外键降级门控放行、失败回放），并已完成已知阻断“本产品信用卡额度限制规则”的共享机制修复与全量验证，冻结新业务候选 `c179989`。后续按既定顺序推进已知任务受控并发评测、保留集、同候选故障/负载/设备与人工复核，不放宽授权或成功语义。

## 接手时先确认什么

1. 读取 [协作约定](../AGENTS.md)，运行 `git status --short`、`git branch --show-current`、`git log -5 --oneline`，核对远端与本地是否一致。
2. 读取本文的状态快照，再读取实际报告和进程。快照只用于定位，不能代替当前状态。
3. 确认是否有仍在运行的评测、设备或构建进程。状态文件写着 RUNNING 仍须核对本机进程或服务器 systemd 的实际 PID；轮询失败不代表进程已停止。
4. 若任务仍在运行，接续观察；若终止，读取原始 FAIL／ERROR 和硬检查后决定下一步。不要直接重跑到通过。
5. 先阅读与当前失败有关的模块及回归，避免扫描全部历史日志或一次重写整条链路。

## 恢复工作后的执行顺序

以下是用户明确恢复开发／验收后的计划，不是本轮已经执行的结果。

恢复后先完成下一节的提速准备：建立失败回放与相关回归入口，核对评分器到发布检查的完整链路，再验证本地独立试验的 8→16→32 路受控并行。按用户提供的模型并发上限 2500 管理总请求，具体生效范围与其他吞吐额度以实际接口为准。之后按以下业务修复与验收顺序推进。准备阶段允许使用小批诊断，不能直接启动完整付费批次；本轮文档更新不代表这些设施已实现。

1. **核对最新业务失败的语义。** 从 `1f1543d` 的 repair 原报告提取 `card_limit_proposal_cancel` 第 2 次试验第 1 阶段，区分“解释本产品卡片日额度”与“询问信用卡授信规则”。先说明本产品无信用卡授信，再在本产品语境下给出有依据的演示卡日额度规则；真正的信用卡咨询仍保持能力边界。若模拟用户改变了任务对象，应记录模拟偏移，不能强迫 Agent 回答另一个问题。取证后才决定修改理解、取证或回答模块。
2. **修共享机制并验证边界。** 覆盖本产品卡片的类别说法、信用卡与贷款不支持、日额度可行性咨询、明确办理、卡片不唯一及跨话题追问；解释不生成提案、不挑选个人卡、不改变账户。检查推荐问题仍仅指向可回答能力。不要把所有“信用卡”字样全局替换成演示卡。
3. **先核对评测与发布检查的一致性。** `19e1dc4` 已实现判官仅额外键越界时剥离并保留诊断；不要再按旧记录当作未实施。当前 `release_gate.py` 仍拒绝 `PASS` 携带非空结构诊断，需做从判官到报告再到发布检查的验证，确认兼容分支不会产生“试验通过但发布必拒”的状态。语义负分、缺字段、错误类型和安全失败仍须保留并阻断；任何协议兼容调整须版本化、审计并单列新证据，不删除诊断或改写旧分数。
4. **形成可复核的新候选。** 在隔离检出目录修改，规则导出检查、相关正反边界／Gateway 回归、Ruff、mypy、全量及有界真实 Flash 诊断通过后，以中文提交并普通 push，再冻结源码、依赖、数据集、提示词及推理档案。文档更新不等于产生已验收的新业务候选。
5. **跑完整冻结验收。** 优先在本地冻结检出目录完成广度 28 项各一次及四个已知数据集各五次，140/140 全部通过才进入保留集 80 项各五次；完整本地证据上传后核对摘要并重新执行发布检查，不因迁移机器自动重跑 140＋400 次。对同一候选完成故障、真实设备及目标服务器环境和实际 HTTP 负载核查，核对报告与源码／APK 摘要。停止于失败或 ERROR，定位后另建候选，不从失败位置续跑拼接分数；已有历史通过不能代替新候选重跑。
6. **完成真实观察、人工复核和交付。** 按用户恢复后的安排，为同一最终候选建立有时间与会话依据的至少七天、五百段真实会话观察；保留全部失败，独立人工复核全部失败和至少 10% 通过试验。全量证据进入 manifest，release gate 与稳定候选打包通过后交付；未满足任一项就明确登记阻断，不宣称整体完成。

## 缩短开发反馈时间的方案

本节方案已在评测运行器、费用账本、发布门控及回归工具链中实现（代码与测试已落地并通过全量验证）。目标是更早发现无效修复、减少不成熟候选进入长批次，并缩短独立试验的排队时间；正式验收次数、评分、安全约束和真实观察门槛不变。业务开发与正式评测仍遵循用户最新指令推进。

### 已核对的耗时环节

截至 2026-11-01，最近服务器控制脚本仍使用 `ThreadPoolExecutor(max_workers=1)`；公共运行器 `scripts/evaluate_dialogue_tasks.py` 的任务与重复试验也是串行，每次试验另起隔离进程，并使用同一输出目录下的 `worker-job.json` 传递任务。不能只调大线程数就宣称已支持安全并行。

历史 `build/model-review-1524f3e-20261031/` 报告中，四组已知任务 140 次的 `elapsed_ms` 合计约 **42 分钟**，保留集前 125 次约 **28 分钟**。这是各试验耗时的总和，不是完整流水线墙钟耗时，不含全部调度、构建与设备开销，也不是后续批次的时长承诺。业务、模拟用户和评分器缺陷都曾在长批次才暴露，单纯换开发模型不能消除这些重复工作。

### 本机资源、模型额度与执行地点

2026-11-01 本机只读核对：**AMD Ryzen 9 9955HX、16 核 32 逻辑线程、系统可见内存约 31.2 GiB（约 32GB 级别）**。用户明确提供模型请求并发限制为 **2500**，此值作为规划依据，尚未通过供应商账户查询或并发压测独立验证；接手时核对账户／模型／接口的适用范围，并计入同账户其他调用。不要把历史串行运行器当作供应商只能串行的证据。

必须区分三个层次：供应商的 2500 个同时模型请求上限、调度器的独立试验数，以及每个 Agent 进程内部两个执行中／八个排队的限制。模拟用户、评分器和回答核验也会产生调用，初始理解还可能触发既有追加请求；试验数不等于同时请求数。增加隔离试验的并行数可保持单个 Agent 的运行档案不变，但仍需跨进程限制全部角色的真实在途请求。不得把 `workflow_runtime.py` 的两个 worker 直接改成 2500，或启动 2500 个 Python 进程。

本机具备开展更多独立试验的条件，优先用本地受控并行提高吞吐。当前主要可改善环节是串行调度、隔离进程启动、job 文件竞争、费用账本和结果汇总；CPU 较强不代表远端模型响应必然更快，未做同配置对照前不宣称本地必然快于服务器。并发额度也不等于每分钟请求或 token 吞吐额度，后者如存在须另行限流。本地正式评测仍调用付费远端模型。

**400 次保留集并非必须在服务器运行。** 它是 80 项任务各五次，现有发布检查按源码摘要、数据集、模型／推理与评分协议及完整记录判定，没有限定运行主机。此前使用服务器是便于后台持续运行和隔离环境的流程选择；本地运行须避免休眠、掉网或编辑冻结源码，进程中断如实保留，不把未完成批次计为通过。

| 本地优先完成 | 目标服务器完成 |
| --- | --- |
| 快速回归、静态与全量检查、广度诊断、140 次已知任务、400 次保留集、连接本机设备的客户端验收 | 接收证据、核对摘要、重新执行发布检查；按用户安排验证部署配置、服务启动、网络、权限、持久化、重启恢复及实际 HTTP 负载 |

本地正式报告可作为同一冻结候选证据，不仅限于开发诊断。上传前保留完整报告、逐项输入输出、失败／错误、调用计量和数据集／源码摘要，另记录操作系统、Python、实际依赖版本、时区及业务日期基准、端点与推理配置；凭据不随包传输，含会话与审计的材料使用受控私有目录，不提交到 Git。上传原始文件并比较 SHA-256，目标端 manifest 指向实际证据位置，不改原报告中的成绩或轨迹。Windows／Linux 下核对 LF 和源码实际字节一致，确认依赖与时间等环境差异对结果的影响。

源代码与完整证据匹配且环境差异核查通过时，不因上传就再次运行全部对话试验；候选或影响结果的配置发生变化，则按发布规则重新验证。正式协议或跨平台证据校验尚有缺口时，先补齐并验证，不能伪造环境等价。上传本身不等于部署，本地对话通过也不能代替目标服务器环境、实际负载、七天真实观察与人工复核。

| --- | --- | --- |
| 原失败回放 | 保存已暴露失败的原始用户消息、各轮输入与预期行为；在隔离初始状态中重建会话，重跑当前 Agent 与真实取数 | 原缺陷消失，硬检查通过；不能只把旧回复重新评分 |
| 相关回归 | 覆盖同类正反边界、跨对象、否定、取消恢复、话题切换及相关 Gateway 轨迹 | 没有新增回归，咨询／办理／确认边界保持 |
| 候选前检查 | 规则导出、静态检查、后端全量与有界真实 Flash 诊断；涉及客户端时补相关设备检查 | 检查通过、变更可审查，中文提交并 push 后冻结 |
| 正式冻结验收 | 28 项广度、140 次已知任务、400 次保留集及同候选设备／故障／负载 | 完整原始证据达到既定门槛，再进入观察与交付 |

固定用户回放用于快速定位和开发反馈，不替代正式动态模型用户，也不计入正式五次。回放只使用已暴露失败及合法开发数据，不提前遍历尚未运行的保留任务来调提示词；已暴露保留失败单独标注来源，不改数据集 split 或把它重新称为盲测。所有回放仍重建隔离账本与主体，不复用旧授权、旧工具响应或旧成功回执作为当前执行证据。

按对象理解、任务状态、证据与数字、模拟保真、评分协议等缺陷类别整理失败清单，一轮修复一个共享机制及其相关边界。开发中的每次修改先做相关验证；形成成熟候选前再跑全量和小批真实诊断，避免每补一种说法就重复整套正式验收。不能把不相关的大量改动捆绑成难以定位的新候选。

### 先验证评测设施，再扩大调用量

建立固定评分样例，覆盖正确回答、漏答、安全违规、模拟目标偏移、合法负分、额外字段、缺字段和错误类型，核对“判官响应 → 试验结果 → 报告 → release gate”的全链路。先处理前节列出的额外字段兼容与发布阻断冲突，避免完成长批次后才发现证据协议不兼容。

固定样例可使用受控模型响应，帮助快速验证评测程序；不能代替真实模型判断质量。合法负分不能因提示调整重新改判，语义与安全检查不降级；协议调整另立版本并产生新报告，保留旧失败、错误和诊断。评测设施通过后，再允许候选进入长批次。

### 独立试验逐步并行

此前“两路到四路”只是保守起点；结合本机资源和用户提供的 2500 请求额度，现调整为从 **8 个独立试验**开始小批诊断，验证后依次评估 **16、32 路**，仍有余量才考虑继续提高。调度逻辑先通过离线竞争及停止行为检查，再启动真实模型诊断。若小批出现内存压力、账本争用、429、超时或错误率上升，先定位并降低并行度；保留该批失败，不靠重跑覆盖。上述并行级别是待测方案，不是已测容量或现有命令参数。

并行单位为完整独立试验，同一会话的提问、确认和执行仍按因果顺序串行。需要先完成以下准备：

- 每个任务／重复编号使用唯一 job 文件、结果文件和临时目录，独立进程、账本、授权、设备与会话状态；结果校验任务身份，不能让多个 worker 覆盖 `worker-job.json`。
- 共享原子费用账本和活动总调用额度，增加跨进程的总模型请求限流。并发许可覆盖 Agent、用户、评分器、回答核验及实际追加／重发请求，超时在途请求在 SDK 真正结束后才释放；上限在用户提供的 2500 以内，扣除账户其他调用占用并保留余量。两个执行中、八个排队的现有 Agent 运行档案保持，不通过增加 worker 绕开供应商额度或污染业务负载测量。
- 首个 FAIL／ERROR 后停止派发新试验，取消尚未开始的排队任务；已在途调用要完成计量并保留实际结果，未完成明确记为未运行／错误，不能静默丢弃或重试到通过。
- 以单一汇总入口原子写报告，稳定排列任务／重复编号，检查缺项、重复、seed、源码与数据集摘要；用预算竞争、文件竞争、失败停止和重启中断场景验证调度行为。
- 并行级别和限流配置写入运行证据；用同一小批诊断清单比较串行基线及 8／16／32 路的完成吞吐、墙钟耗时、进程启动开销、峰值内存、账本等待、超时、错误率和费用。依据实测选默认级别，不以 2500 直接推导进程数或承诺线性提速。

测试与评测源码也在当前候选摘要内，调度器变更须先验证并提交，再生成新冻结候选。未经完整验证的并行报告不能直接作为正式验收证据；单个专用模拟器继续独占串行，HTTP 负载测试避免与其他付费批次争抢资源而改变测量条件。

### 证据、观察期与提速交付

开发诊断可复用历史失败输入和已生成的定位材料；正式结果只能按现有发布检查接受的完整同候选证据引用。文档提交不改变业务摘要时核对现有规则即可；业务、评测代码、依赖、提示词、数据集或推理档案变化后，不能把旧版本的通过片段拼接成新候选成绩。进一步按依赖拆分证据有效性属于另项设计，不在本方案中默认为已获支持。

七天真实观察无法靠增加模型调用压缩。满足离线门槛并按用户安排启动后，可在同一冻结候选上并行整理证据及开展允许的人工抽样复核；最终失败和通过样本仍须完整核对。业务源码变化后重新评估观察证据有效性，不能自动继承旧候选天数或以模拟会话补足五百段真实会话。

提速设施应交付可复用的快速回归入口、失败与相关用例清单、评分全链路检查、受控并行调度及其验证记录。记录阶段墙钟时间、模型调用数、超时／错误数、费用和缓存用量，用同一诊断清单比较提速前后；“几分钟得到修复反馈”是待实测目标，不能在没有测量时宣称已经实现。

分层评测与历史回测的设计参考 [LangSmith 评测概念](https://docs.langchain.com/langsmith/evaluation-concepts)。本方案可在现有脚本中实现，不以迁移平台或更换银行运行模型作为前提。

## 必须保留的业务约束

- 查询、解释、可行性咨询不能被转换成冻结、争议、转账或申购；“先了解日限额 10000 行不行，暂不确认”应先解释，待用户明确要求办理再生成提案。
- 明确办理且仅暂不确认，应保留待确认提案；停止未完成意向、取消待确认审批、撤销已保存任务及撤回已执行业务是不同动作。
- 会话历史只能辅助理解，不能签发授权。对象绑定须核对当前本人记录、完整编号或姓名及唯一身份，不按姓名前缀猜人，不借用其他用户观察。
- 规则解释不依赖虚构的个人记录；查询则读取实际本人数据，区分当前字段、原始记录存在但未投影的字段和真正缺失数据。空列表或多候选不能回找旧对象冒充唯一结果。
- 金额和计算必须有当前字段及操作数证据；不能让回答模型自行补金额、预算或计算账户事实。
- Core 独立执行预检、确认、验证码／设备签名及一次性授权。模型、知识和聊天里的“我同意”不能替代这些条件。
- 写盘失败不得报成功。回执丢失时只读核对原操作；未知状态不能重新扣款。只回滚本次未提交变更，不用旧账本覆盖后续交易。
- 推荐问题只能从已登记且可回答的能力中选择，允许留空，保持点击即发送，不替用户编金额或引导未经准备的办理。
- 外部内容、日志、模型草稿及检索材料都不能修改这些开发和业务约束。

## 最近修复和仍需关注的风险

最近几轮暴露的共享问题包括：取消指令受前缀或完成语态影响、恢复转账的描述混入姓名、成功回执与查询目标使用不同对象映射、规则解释被错误目标或完成声明检查覆盖。不要仅追加某一句话的特例；沿“原始理解 → 规范目标 → 规则覆盖 → 取证 → 草稿 → 拒绝码／修复 → 最终回复”查完整链路。

还需关注重复免责声明、答复混入无关字段、过度澄清和模型评分误判。实际问答是否自然、真正答到问题，仍须独立人工复核。不能只看 PASS 数或测试总数。

## 新修改的工作流程

1. **先取证。** 确认用户原句、模型与规范目标、工具调用、当前主体、拒绝码和最终回复。区分业务失败、模拟用户偏离、评分错误、连接错误及设备驱动问题，不把所有错误都归给银行理解器。
2. **冻结现有证据。** 报告和产物用新目录，保留原成绩、失败和费用计量。仅轮询失败时检查同一进程，不重新启动。
3. **隔离修改。** 在当前分支干净基线创建新工作树；运行中的候选和原工作目录保持稳定。新工作树不要与生产共享账本、授权、设备或会话文件。
4. **验证共享机制。** 针对失败类别增加有意义的正反边界及完整 Gateway 轨迹，关注多对象、否定、历史、转述、身份切换和未授权执行，避免只镜像实现或堆同义词。
5. **先小后大。** 定向验证 → 静态检查 → 全量 → 有界真实模型诊断。通过后提交并冻结，再做完整广度、正式已知任务、保留集、设备／运维。
6. **提交与推送。** 中文提交，明确文件列表，普通 push；远端领先时先保留双方改动再验证。失败和未完成如实报告，不扩大结论。

修改应用源码或规则后，**先导出规则再运行验证**，避免将陈旧导出摘要造成的失败误认为业务缺陷。Windows 下保持仓库 LF 约定，冻结前核对工作文件与 Git 提交的实际字节；不能在完整测试期间继续改业务源码。

现有机器有两个用户自有未跟踪文件：`docs/功能建议.md`、`scripts/contest_live_probe.py`，保留且不提交。不要使用 `git add .`。运行全仓 lint 时，这类用户文件可能报错；用干净的隔离工作树核对本次变更，不擅自改用户文件或弱化 lint。

## GLM、Qwen 或 Gemini 如何参与开发

在开发工具中选择 GLM-5.3-Flash、Qwen3.8-Max 或 Gemini 3.8 Flash，开放完成任务所需的仓库和工具权限，再使用本文接手提示词。无需修改 `model_config.py`、银行 `.env` 或服务端运行配置。开发工具的 API 凭据与银行业务凭据分开管理。

| 开发模型 | 开发工具中的配置与交付要求 |
| --- | --- |
| GLM-5.3-Flash | 在支持该提供商的开发工具中选型，按其接口实际支持的参数配置；使用同一接手提示词、验证和提交纪律 |
| Qwen3.8-Max | 在支持该提供商的开发工具中选型；仓库取证、修改与验收要求相同 |
| Gemini 3.8 Flash | Google 官方模型标识为 `gemini-3.8-flash`；仅配置开发工具的模型，使用本文接手提示词；通过工具读取文件、执行验证并审查 diff |

Google 官方 [Gemini 模型目录](https://ai.google.dev/gemini-api/docs/models) 已列出 Gemini 3.8 Flash 与上述标识（2026-11-01 核对）。接入前核对所用开发工具的 Gemini 提供商支持、账户可用性、文件读写、命令执行及工具调用；中转提供商的别名以实际模型列表为准，不凭显示名推断成功接入。本次只登记开发选项，未配置凭据、切换当前开发会话或实测 Gemini 开发能力。

本项目未做这三个开发模型间的受控对比，不能保证某个模型单独完成所有修复。其他官方接入要求见 [GLM-5.3-Flash 文档](https://docs.z.ai/guides/vlm/glm-5.3-flash)、[Qwen 模型说明](https://help.aliyun.com/en/model-studio/text-generation-model/)。开发助手应以能否正确定位根因、保留安全约束、修改可审查且验证有效来证明能力。

如果将来用户明确要求更换银行运行模型，另建候选、适配提供商参数、结构化输出、思考模式、期限、缓存、价格和调用计量，再重跑相同门槛。各提供商思考模式须按届时官方能力核实，不能直接套用本候选的思考关闭档案。更换开发助手不触发这项迁移。

## 每次交接应留下的记录
