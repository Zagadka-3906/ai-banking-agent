## 二、第二轮新发现问题

### R2-1 【P2】“一笔/全部/调到N”等量词型金额表达不被提取
三个独立用例同一模式：
- 「再转一笔300给李四」→“请补充明确的金额（例如 300 元）。”（金额 300 明确在句中）
- 「把CJ01002全部赎回」→“请补充明确的金额”（应默认全部持仓 ¥2,000 或提示持仓金额）
- 「把尾号3082的卡每日限额调到8000」→“请补充希望设置的卡片额度（例如 5000 元）”（8000 明确在句中）

而普通句「给李四转300元」「转300块给李四」均正常——说明“动词+到N/一笔N/全部N”结构未被 slot 提取覆盖。澄清话术本身友好，但连续三次“用户给了数、系统说没给”对体验伤害大。证据：r2-n01c / r2-n09n / r2-n10c.jpg。

### R2-2 【P1】生日联动（跨场景）日期槽位完全失效——主推场景走不通
三轮递进全部失败：
1. 完整长句「我爱人生日快到了，这个月帮我锁定1000元活期，生日前2天提醒我订鲜花和蛋糕」→“请补充生日日期。我不会替您猜测。”
2. 按澄清补充「10月5号」→ 原样重复“请补充生日日期。”（澄清回路断裂，补充值未被接住）
3. 单轮完整句「10月5号是我爱人生日，这个月帮我锁定1000元活期，生日前2天提醒我订鲜花和蛋糕」→ 仍要求补充日期（日期明明在句首！）

证据：r2-n12 / r2-n12b / r2-n12c.jpg。表内第 6 项“检测我爱人生日→锁资→订花蛋糕”在当前构建**无法完成**。联系人册中爱人生日为 1990-10-05，系统也未尝试利用已登记生日。建议：修复 CROSS_SCENE_LOCK 的 event_date 槽位解析与澄清回填；澄清时应说明可接受的日期格式。

### R2-3 【P2】“查看我的持仓”永远返回在售产品列表
申购前、申购后、赎回后三次查询持仓，均返回“在售理财产品共 4 款”产品列表，从不显示持仓本身（有持仓时应显示 HLDD 编号/金额；无持仓应显示“暂无持仓”）。用户无法确认申购/赎回结果。证据：r2-n09a / r2-n09q.jpg。

### R2-4 【P2】会话 15 分钟 TTL 硬过期：正在填表的用户被直接踢回登录页
8:35 登录，8:54（恰 15 分钟）在风险测评第 8 题处被踢回登录页：“登录状态已失效，请重新登录”，测评进度全部丢失（r2-n09e.jpg）。安全上 TTL 硬过期正确，但：①无滑动续期/过期前提醒；②未提交的表单状态（测评 7/8）不保留。建议：空闲续期 + 把“会话即将过期”提示与“重新登录后恢复未完成流程”作为改进项。

### R2-5 【P2】多卡指定支付卡的澄清回路死循环
申请虚拟卡后（账户有两张卡），转账预检被拒：“您有多张可用的卡片（CARD-001、CARD-150EDB98），请指定用于支付的卡片”。随后按提示明确指定「用尾号3082的卡给李四转500元，备注学费」→ **返回完全相同的拒绝**（r2-n02b.jpg）。“尾号3082”未被映射为 CARD-001 并传入预检的 card_id 槽位——用户照做也无法通过，澄清形同虚设。

### R2-6 【P3】预约转账回执卡时间显示为 UTC
回复正文说“预约时间为 2026-10-02 10:00（北京时间）”，但回执卡与待办任务显示“执行时间 2026-10-02T02:00:00+00:00”（UTC 原始格式）。应统一为本地时间格式（r2-n06b/c.jpg）。

### R2-7 【P3】复杂句风控拒绝时缺少“如何指定卡”的格式引导
（与 R2-5 相关）多卡拒绝话术只说“请指定用于支付的卡片”，未给出可解析的示例句式（如“用尾号3082的卡”）。

### R2-8 【P3】实测过程观察：欢迎页快捷入口（查余额/转一笔/看账单/做规划）点击后的预填行为
「转一笔」等入口会把草稿填入聊天框，但首轮实测中“转一笔”直接发送后若金额缺失，回到与 R2-1 相同的澄清。属提示性观察，非缺陷。

### 环境事件记录（非应用缺陷）
- 实测开始前检测到**另一自动化进程并发驱动同一模拟器**（聊天中出现非本会话的“给验收联系人30446654转200”“给你好转200”，源自动插桩测试的联系人命名模式），且并发构建用联网变体覆盖了 `android/app/build/outputs/apk/debug/app-debug.apk`，导致一次“无法连接核心服务”误报。已通过 `pm clear` + 从源码重建默认变体 + 重装后隔离复测。结论：并行驱动/构建期间同一 APK 路径会被覆盖，建议测试时锁定构建产物路径或使用 `-PachiveName` 区分。
- force-stop 重启后 App 显示“登录状态已失效，请重新登录”（r2-n14a.jpg）：与 15 分钟 TTL 一致（重启时距登录已 15 分钟），无法区分“重启不恢复”与“TTL 到期”，建议结合 R2-4 一并改进（重启后若 token 未过期应静默恢复会话）。

## 四、修复优先级建议

1. **P1**：R2-2 生日联动日期槽位失效（主打演示场景不可用）；R2-5 多卡指定卡澄清死循环（资金路径被卡死）。
2. **P2**：R2-1 量词型金额提取（一句话修复三类用例）；R2-3 持仓查询；R2-4 会话续期与进度保留。
3. **P3**：R2-6 UTC 时间显示、任务页混排、订阅卡“结果代码 200”、弹层返回退出。
4. 回归保障：R2-2/R2-5/R2-1 建议补进 `tests/data/natural_conversation_cases.json` 与 androidTest，防止再次回归。

## 五、总体结论

- 联网 + LLM 模式的**理解能力显著优于第一轮的独立引擎**：动态累计升红、定时转账、备注、取消话术、年度口径、测评题干等第一轮 P1/P2 问题大半已修复；
- **资金安全行为全部正确**：三级分级、动态升红、双因子、错误 OTP 拒绝、非联系人拒绝、审批 TTL；
- 当前最需要修的是**两个澄清回路断裂**（生日日期、指定支付卡）——它们让“澄清→用户配合→仍失败”，比不澄清更伤体验；
- 以及一类共性的 **slot 提取缺口**（“一笔 N / 到 N / 全部 N”），建议在 LLM 提示词中补充 few-shot 并在 validate 层增加“句中含数字却报缺金额”的一致性校验。
