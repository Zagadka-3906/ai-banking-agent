# 安全自评报告（Android/IM 演示沙箱）

> Android 默认交付无需电脑后端的独立演示 APK；签名 IM webhook 与 Android 联网构建共享渠道网关、Agent 编排和 Mock Core。本文不是生产银行系统的合规认证，账户和交易均为虚构数据。

最新实测证据见 [Agent 五项安全机制评测](agent-security-evaluation.md)。

## 1. 资产与信任边界

受保护资产包括账户余额、锁定资金、流水、卡片、联系人、订阅、持仓、会话、一次性授权、设备公钥、推送令牌、审计事件和模型/API 密钥。

```text
Android / IM Provider（不可信输入）
        ↓
Agent Gateway / LangGraph（半可信编排，不持有账本）
        ↓
Mock Core（唯一身份、策略、授权和记账边界）
```

Android 界面状态、IM 文本、模型输出和客户端自报身份都可能被篡改。只有 Core 校验过的会话、策略、一次性凭证和设备签名可以授权变更。

独立 APK 的信任边界完整位于 Android 应用沙箱内：`StandaloneBank` 从应用私有存储读取 Mock 事实，短时审批绑定主体、动作和金额，红区 challenge 由已登记设备公钥验签，审计记录使用前项哈希串联。它不依赖网络模型，也不会把自然语言当作成功凭证。应用私有存储和本地哈希链不能替代服务端 HSM、WORM 审计或真实银行账本；拥有 root 权限的设备或清除应用数据都能重置演示状态，因此该模式只用于离线演示。

主要威胁：Prompt 注入诱导越权；模型或网络层伪造交易结果；盗用、篡改或重放 token；绕过确认/MFA；负数、NaN/Inf、并发重试导致超扣；身份枚举和敏感日志泄露；连续失败或组合行为未熔断；沙箱逃逸；伪造或重放 IM webhook。

## 2. 权限分级

| 等级 | 场景 | 服务端控制 |
| --- | --- | --- |
| GREEN | 余额、流水、账单、产品、卡片和订阅查询 | 有效会话、对象鉴权、事实字段校验 |
| YELLOW | 小额转账、预约/AA 创建、取消订阅、小额锁资 | Core 预检、LangGraph 中断、明确确认、一次性授权 token |
| RED | 大额/累计超阈值转账、理财申赎、高风险卡片操作、改密 | Yellow 全部控制、OTP、Android Keystore P-256 设备签名、一次性 MFA proof |

风险由 Core 重新计算。Agent 和渠道不能通过传入 `risk_level`、布尔确认值或文字说明降低等级。

## 3. 五项安全机制

### 3.1 幻觉防护

- Agent 只选择白名单意图和工具，不能直接访问账本或生成可执行工具名。
- 余额、流水号、持仓、卡状态、订阅结果和任务状态必须来自 Core 响应，并校验必需字段、状态码与数值一致性。
- 超时、异常响应、字段缺失和校验失败进入“未完成/无法核验”分支，不生成成功回执。
- 流式接口每轮只有一个终态帧，避免先发错误成功文案后再更正。

### 3.2 注入防御与权限控制

- 输入经过长度、Unicode、控制字符和 Prompt 注入检测；可疑指令只能拒绝或澄清。
- `Intent`、字段 Schema 与 Core 路由均为白名单；模型不能要求执行 Python、Shell 或任意 URL。
- 网关必须携带 `/auth/login` 签发的会话，并回 Core 校验权威主体。裸 `X-User-Id` 不能登录网关。
- 授权 token 绑定主体、会话指纹、操作、金额、对象和上下文摘要；执行端复核并拒绝篡改、过期和重放。
- 红区只接受已登记 Android P-256 设备签名。`face_verified=true`、旧格式票据、错误设备、错误 jti、过期 challenge 和重复 challenge 均被拒绝。
- IM provider 必须在允许列表，webhook 校验原始 body HMAC、时间窗与事件编号；事件内 `user_id` 被忽略。

### 3.3 操作审计

- 登录、会话、预检、确认、MFA、执行、取消、熔断、沙箱和 IM 绑定/消息均记录结构化审计。
- 事件包含请求编号、主体、动作、风险/决策、结果、时间与脱敏元数据，并通过前序摘要形成 SHA-256 哈希链。
- 网关按 `request_id` 聚合 Agent 与 Core 来源，明确报告 `complete` 和 `missing_sources`，不把缺失日志伪装为完整链路。
- 可选 `BANK_AUDIT_LOG_PATH` 支持追加落盘和重启校验；生产仍需外部 WORM 存储与 KMS 签名。

### 3.4 异常熔断

- 授权失败在滑动窗口累计，达到阈值后暂时锁定主体。
- 大额操作、卡片状态/额度变化、改密、挂失和失败后成功等组合信号加权计分；命中规则写入 `BEHAVIOR_RISK_LOCK`。
- 同一请求信号按 `request_id` 去重，避免重试重复加分；窗口到期后自动恢复。
- 锁定期间预检和执行双点拒绝，防止先取得凭证再绕过熔断。

### 3.5 分析沙箱

- `sandbox.py` 只接受只读 AST 白名单，禁止导入、属性逃逸、文件、网络和任意函数调用。
- 限制表达式节点、整数/幂规模、输入输出字节和执行时间；拒绝日志不回显表达式或账户数据。
- 首选短生命周期进程，并在安全健康接口报告实际模式；受限环境降级线程时明确暴露，不能宣称 OS 级隔离。
- 生产部署仍必须使用独立容器或 microVM、只读文件系统、无网络命名空间、seccomp 与资源配额。

## 4. 其他已实现控制

- argon2id 口令登录、可选登录 OTP、会话短 TTL、登出吊销当前会话。
- HMAC 签名短时授权、一次性消费、MFA proof 绑定父授权、完整业务上下文绑定。
- 余额使用可用金额校验；执行时复核账户与卡片状态。
- 幂等键和并发锁保证网络重试至多记一笔；同一 nonce 并发只有一次成功。
- 账本/任务失败使用快照回滚；生产需数据库事务与 outbox。
- 账本、审批和设备注册表可配置原子落盘与完整性摘要；摘要算法由服务端配置决定，篡改后拒绝载入并冻结写入。
- 到期转账与订单草稿只进入 `WAITING_USER`，重新预检和授权后才结算。
- 响应设置 `no-store`、`nosniff`、frame 限制和请求体大小上限。
- 日志、错误和审计对口令、OTP、token、签名、卡号和 provider secret 脱敏。

## 5. 核心负向验收

| 测试 | 预期 |
| --- | --- |
| 模型声称成功但 Core 失败/超时 | 回复未完成，不出现编造流水号或余额 |
| Prompt 要求忽略规则、输出密钥或执行代码 | 拒绝或澄清，不调用写工具 |
| 网关只带 `X-User-Id` | 401，不建立 Agent 会话 |
| 会话主体与请求对象冲突 | 使用权威主体或拒绝，不越权读取/写入 |
| 0、负数、NaN、Inf 或超限金额 | 400/422，余额不变 |
| 修改 token 中金额、收款人、用途或主体 | 拒绝且不记账 |
| 过期/伪造/重复 token 或 challenge | 拒绝且审计留痕 |
| `face_verified=true` 或非设备票据 | 403，不签发 MFA proof |
| 冻结账户/卡片后使用旧授权 | 执行再次拒绝，余额不变 |
| 同一幂等键/nonce 并发 | 至多一笔账，重复请求回放或拒绝 |
| IM 错签、过期、重放、未知 provider | 401/403/409，不进入 Agent |
| 沙箱文件/网络/导入/大整数/超时尝试 | 阻断并记录脱敏审计 |

## 6. 已知限制

### 上线前必须处理

1. 账本、会话、审批、IM 绑定与去重仍是单机内存/文件演示实现，需要事务数据库、Redis 与跨实例一致性。
2. 本地 OTP 和测试账户只适合沙箱；生产需要 OIDC、真实 OTP/生物供应商、设备生命周期与 KMS。
3. Docker 示例未提供 TLS/WAF、灾备、集中限流和密钥轮换，不得直接暴露公网。
4. 审计哈希链不是外部不可抵赖存储，需要 WORM/KMS 和集中告警。
5. 沙箱的 AST/进程隔离不是生产代码执行环境，需要容器或 microVM 强隔离。
6. FCM、真实支付、理财、商户订单和 IM provider 均需正式供应商接入与合规审查。
