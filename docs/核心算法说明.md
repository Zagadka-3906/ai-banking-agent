# 核心算法说明

版本日期：2026-11-02。本文按“输入—处理—输出—失败边界”说明安言的系统分工、核心机制、授权步骤、验证结果与限制。示例只用于解释算法，不是当前账户数据或真实模型运行结果。

Gateway 是对话网关，Core 是模拟银行核心；模型负责理解与草稿，程序负责证据和计算，Core 负责资金授权、业务执行及回执。讨论状态与执行权限分开，所有场景使用虚构数据。OTP 是一次性验证码，MFA 是多因子验证，Keystore 是 Android 的密钥存储与使用机制。

## 总体处理模型

安言将自然语言理解、证据计算和银行执行分开。模型提出结构化理解或回答草稿，程序核验对象、字段和依据，Core 再独立判定是否允许执行业务。

| 阶段 | 输入 | 输出 | 拒绝或澄清条件 |
| --- | --- | --- | --- |
| 需求理解 | 本轮原话、同主体脱敏上下文、能力与规则 | 言语行为、业务参数、目标列表、讨论命令 | 协议不合法、对象矛盾、金额歧义、范围不明 |
| 讨论管理 | 已校验命令与本人未完成任务 | 暂停、恢复、补充、更正或停止讨论 | 错对象、多候选、历史叙述或仅询问取消规则 |
| 取证与计算 | 目标、白名单工具、资源字段 | 当前规则、本人记录、计算结果及来源 | 越权、读取失败、缺字段、不完整集合 |
| 回答核验 | 目标、证据、草稿 | 可见答复与逐项目标覆盖状态 | 无依据金额、错主体、漏答或无回执成功声明 |
| 办理与提交 | 明确参数、原审批、用户确认和验证材料 | 核心回执或明确失败 | 参数改变、授权无效、风险升级、业务条件不满足或保存失败 |

LangGraph 的主图包含 `intent_parser → risk_checker → human_review／executor → responder`；复合流程通过 `workflow_next` 进入下一步。查询规划与目标回答在对应业务处理中执行，不能将所有用户消息都理解为待审批资金操作。这些节点分别承担理解、风险预检、用户确认、执行、表达和下一步编排；用户确认节点不是实际银行坐席接管。

## 需求理解与任务状态

### 目标协议

模型理解后，程序将本轮请求归一化为最多五项目标。每项含 `id`、`act`、`resource`、`question`、`fields`、`subjects`、`topic`、`requires_record` 等字段；可选计算描述为 `calculation={operation, field}`。

- `act` 区分查询、解释、办理、不支持与不明确。
- 字段只能来自资源目录，例如卡片状态、日额度和渠道；不能由模型新增 URL、SQL、身份或执行能力。
- 用户原文及最近已核验对象用于定位资源，最终账户事实仍需本轮读取。对象有歧义时澄清，不从多个候选中猜一个。
- 查询通常要求真实记录；纯规则解释可以只用版本化政策。解释本人实际状态时必须另有本人记录。

典型目标结构如下，表示一次卡片额度查询，而不是调额授权：

```json
{
  "id": "q1",
  "act": "QUERY",
  "resource": "cards",
  "question": "查询这张卡的日额度",
  "fields": ["daily_limit"],
  "subject": "card_001",
  "subjects": ["card_001"],
  "topic": "card",
  "requires_record": true,
  "needs_subject": false
}
```

这是一个结构示例，`card_001` 仅是示例编号，不能证明该卡存在。`subject` 是唯一对象，`subjects` 是对象集合，`needs_subject` 表示是否尚待明确对象；`question` 保留当前问题，`topic` 限定主题。

结构校验限制目标数为 1–5，每目标字段来自资源白名单、最多八项且不可重复，对象集合最多五项。`act` 只能为 `QUERY`、`EXPLAIN`、`ACTION`、`UNSUPPORTED`、`UNCLEAR`。可选计算只允许登记操作及字段。模型给出合法 JSON 只说明结构可解析，不证明对象、金额、权限或事实正确。

### 讨论恢复与执行分离

讨论状态按主体保存最多四项未完成任务，包含业务、对象、缺失字段和状态。`RESUME`、`FILL`、`CORRECT`、`PAUSE`、`CANCEL` 必须匹配本人现有任务及本轮表达；无任务编号时只能在唯一匹配条件下继续。

例如，先说“给李四转账，金额未定，先问一下验证要求”，当前轮先解释规则；之后“李四那笔补 300 元”可补齐唯一匹配的意向，再重新预检并等待确认。输入金额不能来自历史猜测，旧授权不能随讨论恢复。

“先不确认”保留待确认提案；“不办理这笔了”只停止匹配的未完成讨论。已创建预约的撤销另走 Core 协议，已结算交易不能通过取消讨论回滚。问卷同样保留用户已经填写的答案，模型不能替用户补题。讨论任务只保存需求、对象和缺失字段，不保存验证码、签名、确认标记或可继承的执行权限。

## 版本化规则检索

版本化业务知识与能力目录共同生成稳定编号的规则记录，当前快照为知识版本 `2026-11-01.2`，共 105 条（75 条规则、30 项能力）。规则包含主题、受众、适用范围及源码引用，导出的人读说明和 JSON 通过一致性检查维护。

检索采用词法相关性排序：将标题、正文与主题别名转换为词项，弱化“查看、我的、如何”等导航词，按词项稀有度、正文命中及标题命中计分。

```text
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
正文分 = Σ idf(t) × min(tf(t,d), 2) / (1 + 词项总数(d)/200)
标题分 = 2 × Σ idf(t)，仅计算标题命中词
总分 = 正文分 + 标题分
```

`N` 是规则记录数，`df` 为包含词项的记录数，`tf` 为当前记录的出现次数。结果按总分降序、编号稳定排序，保留不低于最高分 35% 的记录，再按调用上限截取；没有有效命中可返回空集合，不能强行拼接无关政策。

理解前可本地检索相关条目，咨询规划还能继续查规则。回源校验只传稳定规则编号，并核对版本、内容与实现摘要；规则可以说明业务条件，不能证明本人余额、订阅状态或付款完成。

## 有界取证与来源管理

普通咨询工具固定为十二类：`knowledge`、`rules`、`account_context`、`balance`、`cards`、`disputes`、`transactions`、`contacts`、`wealth_products`、`wealth_holdings`、`risk_profile`、`tasks`。传输限制为受控 GET，主体来自当前会话。

订阅记录没有免确认读取工具，仍需原黄区确认。查询持仓不能用公开产品货架替代，联系人保存状态不能从转账流水推断。

目标协议下，初读、失败重试和修复共享读取预算：

```text
读取上限 B = min(10, 4 + 2 × 目标数)
规划最多三轮，回答草稿最多三次
同一失败读取最多重试一次，重试计入 B
```

此处是逻辑读取次数，不等同 HTTP 请求数；例如规则读取可能按固定批次分批核验。兼容旧路径另有五次读取、两轮规划的限制，不能混作新的预算。

证据记录保留资源、主体或对象、字段、来源编号和必要的集合范围。同资源刷新后更换证据编号并替代旧事实，防止改写时继续引用过期值。历史数据可以帮助解析“刚才那笔”，不能直接成为本轮最新状态。

投影契约区分已展示字段、同条记录的必要背景和未展示字段。“未展示金额”不能写成“原记录没有金额”；失败证据只证明某次读取失败，不能证明没有记录或已恢复。读取失败、有效空结果和实际记录各自保留不同来源与状态，后续成功读取也不能与先前失败混为同一事实。

## 金额计算与沙箱

### 结构化计算

受控计算支持 `difference`、`sum`、`count`，只能使用登记字段与当前已核验记录。计算不接受模型提供的任意代码或数值作为账户事实。

```text
输入：目标 G，当前证据 E
选出与 G 的资源、字段、对象一致的原始证据
若对象不唯一、操作数重复、缺字段或数值非有限：不生成结果
若计算全量金额：要求集合完整，记录数量与集合统计一致
difference：两个操作数的绝对差
sum：Decimal 累加
count：已核验对象数或有效集合统计
输出：结果、goal_id、input_evidence_ids
```

例如两张卡的已核验日额度分别为 1000.00 元与 3000.00 元，差额为 `abs(1000.00 - 3000.00) = 2000.00` 元。结果证据同时绑定两项输入；引用结果会展开原始来源，最终校验重新核对计算。输入缺失时保留缺口，不能让模型自行补出 2000 元。

合计不能用被截断的展示列表推断；数量可使用完整集合统计。零条记录、读取失败和缺失记录是不同情况。

### 账单表达式执行

账单分析另有受限表达式路径：AST 白名单限制语法与调用，禁止任意导入、属性访问和不受控执行；输入、表达式、节点及输出规模有界。默认墙钟期限为 1.5 秒，工作进程限制 512 MiB、CPU 3 秒，正常最多处理 50 次任务后重建，超时或崩溃后也重建。

这些值是不同层的限制，不能把 CPU 限额当作单次用户等待时间。限制安装失败时默认拒绝；诊断线程回退默认关闭。沙箱没有独立文件系统和网络隔离，计算结果也不能授予资金权限。禁止通过计算接口传入新身份、写操作或任意执行地址。

## 草稿生成、核验与修复

草稿包含回答、来源引用、未完成项和逐目标覆盖。确定性检查先约束金额锚点、字段、编号、主体、来源与操作完成声明；金额占位符由服务器使用绑定证据填入。独立模型调用再检查是否切题、证据是否支持以及目标是否覆盖，失败草稿不直接下发。

| 反馈 | 下一步 | 不允许发生 |
| --- | --- | --- |
| `READ` | 在共享预算内补查缺失事实 | 为改写措辞无限重复读取 |
| `CALCULATE` | 补充受限计算及操作数来源 | 用模型自由计算代替受控来源 |
| `REWRITE` | 保留证据改写错误表达或引用 | 擅自换对象、扩大范围或降低原问题要求 |
| `CLARIFY` | 明确需要用户补充的信息 | 把未澄清目标标作已完成 |

每项目标分别标记 `ANSWERED`、`NEEDS_DATA`、`NEEDS_CLARIFICATION`、`NEEDS_CONFIRMATION`、`UNSUPPORTED` 或 `TOOL_FAILED`。完整回答、部分成功和仍需输入分别输出；固定字段或相关规则回退单列，不冒充自然回答完整通过。资金执行成功与失败由 Core 回执确定，不能由回答模型重写为另一种业务结果。

默认模型为 `deepseek-flash`，示例配置思考模式为 `disabled`。初始理解等待 4 秒且模型池只有当前调用时，最多追加一次相同输入请求，共用原 12 秒期限；采用首个传输成功结果后仍校验，不比较答案优劣。运行中未采用的调用占位到 SDK 结束，晚到结果只计量，不改答或评分。这一有界策略不能保证开放表达始终理解正确。

## 核心风险与授权算法

转账预检使用当日已转出金额、有效未消费的转账授权、未结算预约安排及本次金额，防止并发拆单绕过累计门槛：

```text
A = 当日已转出 + 当前未完成转账安排 + 本次金额
基础等级 = YELLOW，当 A ≤ 1000 元
基础等级 = RED，当 A > 1000 元
若命中行为升级条件，则提高验证要求
```

例如先取得一笔 600 元待确认授权，尚未完成时又预检 600 元，第二笔不能仅按本笔金额判黄区，而要计入前一笔未完成安排。这是风险算法示例，不是当前账户执行记录。

到期预约的执行会排除自身的重复计入，再核验其他未完成安排。业务类型也可直接规定红区，例如理财申赎、调额和冻结；关闭渠道为黄区，开通为红区。它不是模型评分得出的概率，不能由模型或客户端降级。Core 按业务规则定级，资金预检与用户确认之间不改变授权主体或请求参数。

授权将金额经 `Decimal` 量化到分，绑定主体、目标、业务、备注摘要、上下文摘要、会话及有效期。用户确认由 Core 保存，红区验证再产生与原授权关联的 MFA proof。执行时重新检查全部绑定与当前余额、卡片、额度及业务条件，不因预检曾通过而跳过校验。

## 幂等提交与异常结果

幂等键按主体和端点隔离，请求参数形成稳定摘要。同键同请求完成后返回原回执；同键改参数拒绝，正在处理的同键请求不能并发再次扣款。支持持久回执的操作随账本一起保存，单次授权为另一道重放约束。

配置持久化后，业务、任务与回执在同一临界区提交：

```text
校验当前会话、原授权、确认、MFA 与业务条件
保存业务及回执变更的可回滚状态
执行本次变更，记录幂等结果
写入临时快照，刷新并替换原文件
成功：发布核心回执与成功审计
写盘失败：回滚业务、任务和幂等状态，返回明确失败
```

写盘失败后已消费的安全材料不恢复，重新办理须重新确认；响应丢失则先读取原操作结果，不能自动新建付款。单进程快照方案不提供多实例事务或绝对断电保证。授权只能使用一次；幂等键按主体和端点隔离，回执与业务状态一起保存，不能只保存余额而丢失核对依据。

## 机制验证与结果解释

截至 2026-11-02，针对本文主要机制的一次专项执行为 237 项通过，1 条既有依赖弃用警告。专项使用隔离账户、临时持久文件和受控模型替身，涵盖下列确定性边界；不是 237 次真实模型任务成功，也不代表完整后端重新执行。

| 机制 | 检查输入或故障 | 验证目标 |
| --- | --- | --- |
| 讨论恢复 | 缺金额、跨话题插问、取消、错对象及多候选 | 只恢复匹配意向，重新预检，不继承旧确认 |
| 计算与来源 | 缺操作数、重复对象、截断集合、改金额或来源 | 不生成无依据结果，不用旧值或子集代替当前全量 |
| 只读累计 | 跨日期读取、无当前桶或已有业务数据 | 查询不初始化、清空或写入累计 |
| 红区签名 | 错主体、错设备、撤销设备、过期或重放 | 拒绝验证，原授权不能跨交易使用 |
| 持久化 | 写盘失败、损坏快照、重启与回执读取 | 不假报成功，回滚或冻结，并可核对已提交结果 |
| 响应丢失 | 结果已提交但客户端没有收到响应 | 查询或回放原回执，不自动重复付款 |

完整后端历史记录为 3147 passed、1 skipped；最终 shaping 客户端历史 JVM 为 140 passed，最终版本未重跑设备专项。历史全量、专项和客户端结果属于不同范围，不能相加为同一次通过数量。

## 重复评测与尚未完成的范围

真实模型评测应冻结源码、数据、依赖、模型与推理档案。每项任务的查询、解释、补充、办理及取消阶段分别检查目标覆盖、Core 方法与状态变化，区分业务失败、模拟用户漂移、评分错误和字段回退；错误和未运行项不能从分母删除。生成模型与评分器可能发生相关错误，需要人工复核。

当前项目稳定发布门槛包括：已知回归每项至少五次完整成功；新任务至少八十项、每项至少五次，完整成功率至少 98%、平均 pass^5 至少 90%；十一类业务分别覆盖且各类成功率至少 95%。安全违规、错误授权、未确认执行和写盘失败报成功均为阻断项。

此外还要求写盘失败、超时、重启、断线、重复投递测试，以及单会话、三会话、十会话和超载检查；客户端实际验证登录、查询、审批取消、强验证和回执。同一冻结候选还需至少七天、五百段会话观察，并人工复核全部失败和至少 10% 的通过试验。

这些是项目验收要求，不是本文声称已经完成的结果。实现者编写的八十项数据也不构成外部独立盲测。单元测试与受控替身不能证明真实服务下的理解、质量或延迟，当前没有充分证据宣称完整稳定门槛已满足。
